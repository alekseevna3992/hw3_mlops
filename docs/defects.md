# Дефекты пайплайна и как они исправлены

## Дефект 1. Данные утекают в git

**В чём был.** Три несогласованных решения вокруг версионирования данных:

- `.gitignore` не содержал `data/` — при первом же `git add .` все JSONL ушли бы в git.
- DVC remote не был настроен: `dvc remote list` пуст, значит, `dvc push` физически некуда выгружать содержимое `data/`, и единственным местом хранения датасета оставался git.
- В `dvc.yaml` у стадии `split` в `outs` были объявлены только `data/train.jsonl`, а `data/val.jsonl` и `data/test.jsonl` — нет. DVC их не отслеживал.

**Как проявлялся.** `git log --stat` показывал крупные JSONL в истории. Симптом из README буквально: «После `git add . && git commit` в истории git оказываются файлы датасета».

**Как исправлен.**
- В `.gitignore` добавлена строка `data/`.
- Настроен локальный DVC remote: `dvc remote add -d local ../dvc_remote`.
- В `dvc.yaml` в стадии `split` добавлены `data/val.jsonl` и `data/test.jsonl` в `outs`.

**Числом подтверждается.**
- `git ls-files data/` → 0 строк.
- `make check` п.1: все четыре подпункта зелёные, `dvc remote list` показывает `local ... (default)`.

## Дефект 2. Смена версии в params.yaml не пересчитывает пайплайн

**В чём был.** В `dvc.yaml` у стадии `collect` отсутствовал блок `params: [collect]`, а у стадии `clean` — `deps: [data/raw.jsonl]` и `params: [paths.raw]`. DVC не видел, что:

- `collect.version` поменялся, значит `collect` надо перезапустить;
- `data/raw.jsonl` изменился, значит `clean` надо перезапустить на новом входе.

**Как проявлялся.** `set_version v2 && dvc repro` говорил `Stage 'collect' didn't change, skipping` и брал `data/raw.jsonl` из старого кэша. `clean.jsonl` оставался идентичным v1, `dvc metrics diff` показывал одни и те же числа.

**Как исправлен.**
- В `collect` добавлен `params: [collect]`.
- В `clean` добавлены `deps: [data/raw.jsonl]` и `params: [paths.raw]`.
- В `params.yaml` добавлены ключи `collect.sources.v1`/`v2`, на которые ссылается `src/config.py` и `scripts/set_version.py`.

**Числом подтверждается.** `make check` п.4:
- v1: `data/clean.jsonl` md5 = `5d86a8e5`, 1520 строк;
- v2: `data/clean.jsonl` md5 = `48f48ac8`, 1520 строк.

Хэши разные — значит, пайплайн реально пересчитался. До правки они совпадали (`9934b41e` и там, и там).

## Дефект 3. Контаминация train/test

**В чём был.** `src/split.py` делал случайный сплит **по строкам** (`row_split`), полностью игнорируя `params.split.group_key = "topic"`. При 76 группах по ~20 примеров одна и та же формулировка вопроса уезжала и в train, и в test — то самое «один и тот же вопрос (или его парафраз) попал в оба сплита».

**Как проявлялся.** `scripts/check_contamination.py` находил `near_dup_pairs > 0` между train и test. Метрики на test были бы завышены, и пайплайн этого не замечал.

**Как исправлен.** `src/split.py` переписан: строки группируются по `normalize_group(topic)`, перемешиваются **группы**, и вся группа целиком уезжает в один сплит (train/val/test). Разные формулировки одного вопроса гарантированно остаются в одном сплите.

**Числом подтверждается.** `make check` п.5 и `metrics/split.json`:
- `id_overlap: 0`, `text_overlap: 0`, `group_overlap: 0`, `near_dup_pairs: 0`;
- v1: train 838 строк / 61 группа, val 103 / 8, test 88 / 7;
- доли: train 0.8144, val 0.1001, test 0.0855.

## Дефект 4. Near-dup дедупликация не работала

**В чём был.** В `src/clean.py` near-dup шаг вызывал `cross_near_duplicates(texts, texts, ...)` — функцию, написанную для сравнения **двух разных** наборов (`left`, `right`). В режиме self-compare она возвращала пары `(i, j)` для почти одинаковых строк, а дальнейшая фильтрация `near = {j for i, j in pairs if i != j}` отбрасывала корректно работающий случай `i == j` и оставляла именно те элементы, которые должны были быть удалены.

**Как проявлялся.** На тестовом наборе `tests/check.sh` (п.2) пара из точной копии `base` и её near-дубля `near` (та же формулировка с другими пробелами и `0)` вместо `0.`) переживала `clean` дважды: `dropped_near_dup` был 0.

**Как исправлен.** Импортируется и используется `near_duplicates` — жадный проход по одному набору: MinHash-LSH, первый представитель кластера остаётся, остальные удаляются.

**Числом подтверждается.** `make check` п.2: `dropped_exact_dup = 1`, `dropped_near_dup = 1` на тестовом наборе, `pii_hits` суммируется в 3. На боевом v1 (1520 → 1029): `dropped_exact_dup = 471`, `dropped_near_dup = 35`.

## Дефект 5. Гейт разнообразия не падал на вырожденном наборе

**В чём был.** В `src/diversity.py` после сбора `violations` стоял `print("diversity: предупреждение — ...")` вместо `raise DiversityError(...)`. Гейт видел нарушения, но не останавливал пайплайн: набор-вырожденец доезжал до `split` и до обучения.

**Как проявлялся.** `make check` п.6 подсовывал тысячу строк с одним системным промптом, одной темой и ответами одной длины — стадия `diversity` завершалась с кодом 0 и ничего не сообщала.

**Как исправлен.** В `src/diversity.py` блок `if failed:` теперь делает `raise DiversityError("diversity: гейт не пройден:\n" + "\n".join(...))`. Каждое нарушение — отдельной строкой, чтобы `grep` в `tests/check.sh` видел ≥ 2 вхождений.

**Числом подтверждается.**
- `make check` п.6: «гейт упал и назвал 4 нарушенных порога»;
- `make check` п.7: 1029 строк, 5 системных промптов, 76 групп (крупнейшая 1.75%), `p90/p10 = 2.74`.

## Побочный эффект среды

В `print`-ах стадий использовались не-ASCII символы (`→`, `≥`, `—`, `…`). На Windows-консоли с cp1251 Python падал с `UnicodeEncodeError` ещё до записи артефактов. Заменено на ASCII (`->`, `>=`, `-`, `...`) через `sed -i` по `src/*.py`. В пятёрку заложенных дефектов это не входит, но без правки ни одна проверка не прошла бы на этой машине.
